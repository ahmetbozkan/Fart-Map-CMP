# STORY-01-02-02: Public profile and the free starter catalog

Status: In progress   Epic: EPIC-01-02   Features: PROFILE-01 (avatar), MON-01 (free tier, launch catalog)   ADRs: ADR-0016, ADR-0024, ADR-0025

## Goal
Every Active user gets a public profile, `users/{uid}`, holding a generated funny display name and a free starter avatar (ADR-0025). The free starter cosmetics exist as real `cosmetic_items` docs in `fart-map-dev`, so the rules accept that avatar.

## Scope
- **In:**
  - **Starter catalog data:** `backend/catalog/starter-catalog.json` is the single source for the free starter items:
    - 2 free avatars and 3 free sounds (`Monetization.md` §free minimums, ADR-0024);
    - every `DataContracts.md` §3.13 field except the store product ids, which are paid-only.
  - **Seed script:** `backend/functions/src/admin/seedCatalog.ts`, run with `npm run seed:catalog -- --project <id>`.
    - Uses the Admin SDK with Application Default Credentials.
    - Idempotent: upserts each item and leaves other docs alone.
    - Refuses the prod project (`fart-map-1a558`); the prod catalog ships with EPIC-01-06.
    - Not exported from `index.ts`, so it is never deployed.
  - **Emulator rules test:** the seeded starter docs make a profile create with each starter avatar pass, and a starter sound is rejected as an avatar.
  - **Unit test on the catalog file:** the free counts meet the minimums, every `item_id` is unique and matches its key, and the types are valid.
  - **Domain (`core/domain/profile`):**
    - `ProfileRepository`: `observeProfileExists(uid)` and `createProfile(uid, NewProfile)`.
    - `DisplayNameGenerator`: a pure function with an injected `Random`; output is `<Adjective> <Noun> <10–99>`, at most 50 chars.
    - `StarterAvatars`: the free starter avatar ids, kept in step with the JSON file by a host test.
  - **`ProfileBootstrap` (`core/data/profile`):**
    - On `SessionState.Active` with a known uid, it watches the profile doc.
    - When the server confirms the doc is missing, it creates the doc once per uid per process, with a generated name and a randomly chosen starter avatar.
    - Started eagerly through Koin.
  - **`FirestoreProfileRepository` (`firebaseData`):**
    - `ProfileDto` with the exact create field set the rules require (counters 0, `is_following_list_public` false, server timestamps; no `bio` or `signature_style_id`).
    - The listener ignores a cache miss, same as the account doc.
    - The write goes through `AppWriteScope`, so a rejection is reported through `PendingWriteMonitor`.
  - **Docs:** `DataContracts.md` §3.1 / §3.13 get the creation path, the starter catalog source and the seed command. STATE records the owner action to run the seed on dev.
- **Out:**
  - Profile tab UI: name, avatar and fart count (PROFILE-02, EPIC-01-07).
  - Editing the name or avatar.
  - Avatar art: `asset_ref` names a bundled asset id that comes with the UI.
  - Paid catalog items and prices (EPIC-01-06, owner pending).
  - A banned-term filter for user-entered names (no free text in this story).
  - Seeding from CI.

## Acceptance
1. Given a user whose session becomes Active (new after the age gate, or an existing account without a profile), when the server confirms `users/{uid}` doesn't exist, then exactly one create is written:
   - `user_id` = uid;
   - a generated `display_name` (1–50 chars);
   - `avatar_id` from the free starter avatars;
   - `follower_count` = `following_count` = 0;
   - `is_following_list_public` = false;
   - server timestamps.
2. Given a profile that already exists, or a cache-only miss (new device, offline), then no write happens.
3. Given the create is rejected (for example, the catalog isn't seeded), then:
   - the existing `AppWriteScope` path reports it through `PendingWriteMonitor` as `write_rejected`, op `profile.create`;
   - it is not retried during that process;
   - the session stays Active;
   - the next launch tries once more.
4. Given the generator with any seed, the name is `<Adjective> <Noun> <NN>`, 1–50 chars, built only from the curated word lists. Names hold no PII and nothing derived from the uid.
5. Given `backend/catalog/starter-catalog.json`, it holds ≥2 free AVATAR and ≥3 free SOUND items, all active. The Kotlin `StarterAvatars` ids equal the JSON's free avatar ids (host test).
6. Given the emulator with the starter catalog seeded from the JSON, a profile create with each starter avatar succeeds, and a starter sound id as `avatar_id` fails.
7. Given `npm run seed:catalog -- --project fart-map-1a558`, the script exits non-zero without writing.
8. `scripts/verify.sh --full` is green, and CI (Android, iOS, backend, secret scan) is green.

## Decisions
- **Who creates the profile?** The client, as the owner (`DataContracts.md` §3.1 line "The owner creates it"; rules from STORY-01-01-04 already validate it). No function.
- **When?** On Active, once the server confirms the doc is missing, not only inside the age gate. This also covers dev accounts made under STORY-01-02-01, and recovers after a rejected create on the next launch. It fits ADR-0025 "EPIC-01-02 writes both documents at sign-up".
- **Display name format?** `<Adjective> <Noun> <10–99>` from curated lists in the product voice, inside the ContentSafety humor boundary (absurd, never targeting a person or body type). It is not unique, since identity is `user_id`. The number cuts down visible collisions. Source: none specified; the simplest safe option.
- **Name language?** English word lists stored as data, the same in every locale for now. Localized names would change a stored value, so they wait.
- **Starter item ids?** `avatar_free_bean`, `avatar_free_cloud`, `sound_free_classic`, `sound_free_squeak`, `sound_free_thunder`. `asset_ref` = the item id, a bundled asset id per §3.13. `rewarded_unlockable` = false, since they're free.
- **Which avatar?** Picked at random from the free starter avatars. No picker in this story.
- **How to seed dev?** An owner-run Admin SDK script with ADC, not CI. The CI deploy service account's Firestore data roles aren't recorded, and widening them is a console action. The owner is a project owner, so ADC needs no new grant. CI seeding can follow once the role is confirmed.
- **Prod?** The script refuses prod. The prod launch catalog, paid items and prices belong to EPIC-01-06 (STATE pending: launch catalog prices).
  - **Known gap:** until prod is seeded, profile creates in the prod flavor are rejected, at most once per launch thanks to the `attempted` guard, and logged as `write_rejected`.
  - Nothing is released yet, so this is accepted. STATE gets a release-blocking item: "seed the prod catalog before any prod release (EPIC-01-06)".
  - Gating the bootstrap by flavor was rejected: a second code path to remove later, for a build nobody runs.
- **Single source of truth for starter ids?** The JSON file. The Kotlin constants are checked against it by a host test, which reads the file from the repo.

## Plan
**backend/**
- `catalog/starter-catalog.json`: `{ "items": [ {item_id, type, name, asset_ref, is_free: true, rewarded_unlockable: false, sort_order, is_active: true}, … ] }`, 2 AVATAR + 3 SOUND. Item names carry the product voice ("Bean Bandit", "Cloud Nine", …).
- `functions/src/admin/starterCatalog.ts`:
  - `loadStarterCatalog(path?)` reads the JSON through `__dirname/../../../catalog/…`, which works from both `src/admin` and `lib/admin`;
  - `validateCatalog(items)` throws on duplicate ids, unknown types or missing fields;
  - `catalogDocs(items, timestamp)` returns `{ "cosmetic_items/<id>": data }` with `updated_at`.
- `functions/src/admin/seedCatalog.ts`:
  - a CLI with `--project <id>`; refuses a missing project or `fart-map-1a558` (exit 1, no writes);
  - `initializeApp({ projectId })` with ADC, then a batched `set(..., { merge: true })` of each item with `FieldValue.serverTimestamp()`;
  - logs the item count through `src/lib/log.ts`.
  - `index.ts` doesn't import it, so it is never deployed.
- `package.json`: `"seed:catalog": "npm run build && node lib/admin/seedCatalog.js"`.
- Tests:
  - `test/starterCatalog.test.ts` (unit): free minimums (≥2 AVATAR, ≥3 SOUND, all `is_free` and `is_active`); unique ids; `catalogDocs` keys; validation rejects bad input; the seed's project guard (the guard is exported as a pure `assertSeedTarget(project)` for testing);
  - `test/emulator/catalog.rules.test.ts`: seeds `catalogDocs(load())` with rules disabled, then checks:
    - a profile create with each starter avatar succeeds, from both a `user` and an `anonymous` context;
    - a starter sound as the avatar fails;
    - a starter avatar flipped to `is_active: false` fails;
    - a client still can't write a catalog item.
  - Other user, signed-out, paid avatar without an entitlement, and extra fields are already covered in `users.rules.test.ts`, so they aren't duplicated.

**shared/** (`core/domain/profile`, `core/data/profile`)
- `ProfileRepository`:
  - `observeProfileExists(uid): Flow<Boolean>` emits true when the doc exists (incl. a pending write) and false only on a server-confirmed miss;
  - `createProfile(uid, NewProfile(displayName, avatarId)): AppResult<Unit>` is fire-and-forget through `AppWriteScope`.
- `DisplayNameGenerator.generate(random: Random): String` with ~24 adjectives × ~24 nouns + `random.nextInt(10, 100)`. A const `MAX_DISPLAY_NAME_LENGTH = 50` mirrors the rules.
- `StarterAvatars.ids: List<String>` and `pick(random)`.
- `ProfileBootstrap(auth: AuthGateway, session: SessionRepository, profiles: ProfileRepository, scope, random)`:
  - `start()` combines `auth.user` and `session.session`, keeps uid only while Active, then `flatMapLatest { uid -> uid?.let(profiles::observeProfileExists) … }`;
  - on false it calls `createProfile` if the uid isn't already in `attempted` (a process-local set), which prevents a loop after a rejection;
  - **How a rejection is reported:** `createProfile` is fire-and-forget. It returns `Success` once the write is enqueued, and a server rejection comes back later through `PendingWriteMonitor` as `write_rejected`, op `profile.create`. That path is the existing `DefaultAppWriteScope`, already covered by `DefaultAppWriteScopeTest`. The bootstrap never sees the rejection, which is why the `attempted` guard exists. A synchronous `Failure` (not expected today) is logged as `profile_create_failed` rather than ignored.
- Koin: `single(createdAtStart = true) { ProfileBootstrap(...).also { it.start() } }` in `dataModule`, with its own `SupervisorJob` scope like the session's.
- Tests (`commonTest`, `kotlinx-coroutines-test`, fakes in `core/fakes`):
  - `ProfileBootstrapTest`:
    - Active + confirmed missing → one create with the right uid, starter avatar and a valid name;
    - exists → no create;
    - no emission (cache miss) → no create;
    - missing → create → still missing (rejected) → no second create;
    - NeedsAgeBand / SignedOut → no create;
    - sign-out then a different uid becomes Active → its own create;
    - a `createProfile` failure is logged and doesn't crash;
  - `DisplayNameGeneratorTest`: 1,000 seeded runs all match the regex `^[A-Z][a-z]+ [A-Z][a-z]+ [1-9][0-9]$`, stay ≤50 chars, and use only list words; word lists are distinct and non-empty;
  - `StarterAvatarsTest`: `pick` stays in the list.
- `androidHostTest/.../StarterCatalogParityTest.kt` finds `backend/catalog/starter-catalog.json` by walking up from `user.dir`, so it works from Gradle and from an IDE run at the repo root. It parses the file with kotlinx-serialization JSON (already a dependency) and asserts the free AVATAR ids == `StarterAvatars.ids`. It runs on the JVM host only; iOS `allTests` doesn't include it.
- Koin: `createdAtStart` singles are built by `startKoin` after every module is loaded (`sharedModules + firebaseDataModules` on both platforms), so `ProfileRepository` from `firebaseData` resolves. The Android emulator run checks this, and the iOS CI link does too.
