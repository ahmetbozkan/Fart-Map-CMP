# STORY-01-03-01: Fuzzed location projection and a dev fart seed

Status: In progress   Epic: EPIC-01-03   Features: MAP-02, PRIV-02   ADRs: ADR-0019, ADR-0023

## Goal
One geohash-6 fuzzing function exists twice, in shared Kotlin (the client computes the public point at write time) and in the TypeScript backend (the re-validation trigger and admin scripts). Both are proven to give the same answer. `fart-map-dev` can be filled with fuzzed PUBLIC test farts, so the map stories that follow have markers to show before Log Fart (EPIC-01-04) exists.

## Scope
- **In:**
  - **Kotlin, `shared` `core/domain/location`:**
    - `Geohash`: `encode(lat, lng, precision)` and `bounds(cell)`, which decodes a cell to its lat/lng box. Pure Kotlin, no dependency.
    - `LocationFuzzer.project(fartId, lat, lng): PublicLocation(publicLat, publicLng, coarseLocationKey)`, per ADR-0019 §3: the geohash-6 cell center plus a deterministic jitter from the fart id, always inside the cell, never equal to the precise point.
  - **TypeScript, `backend/functions/src/lib/location.ts`:** the same `encodeGeohash`, `geohashBounds` and `projectPublicLocation`.
  - **Shared test vectors:** `backend/functions/test/fixtures/location-fuzz-vectors.json`, generated once from the TS module and checked in. The TS unit test and a Kotlin JVM host test both assert every vector, so the two implementations can't drift apart.
  - **Dev seed:** `backend/functions/src/admin/seedFarts.ts`, run with `npm run seed:farts -- --project fart-map-dev [--center <lat>,<lng>] [--count <n>]`.
    - Same allowlist as the catalog seed (`fart-map-dev`, `demo-*`); prod is refused.
    - Writes PUBLIC farts with fixed ids `seed_fart_NNN` by a fixed seed author `seed_author_dev`. Each fart gets the full `DataContracts.md` §3.2 field set with fuzzed public fields and its precise point in `private/location`.
    - Idempotent (upserts the same ids). Uses starter avatars and sounds from `backend/catalog/starter-catalog.json`.
    - Not exported from `index.ts`, so it is never deployed.
  - **Docs:** `DataContracts.md` §3.2 names the algorithm and both implementations; `OwnerTodo.md` A gets the dev fart seed step; ROADMAP gets the EPIC-01-03 split.
- **Out:**
  - The re-validation trigger that recomputes the public fields from `private/location` (ADR-0019 §4). It ships with the create path in EPIC-01-04 and uses the TS module from this story.
  - The map UI, the viewport queries and the geohash range cover (STORY-01-03-02/-03).
  - Device location (STORY-01-03-04).
  - Cleaning up seed data, and seeding from CI (same reason as the catalog seed, STORY-01-02-02).

## Acceptance
1. Given known reference points (Wikipedia's `57.64911, 10.40744` → `u4pruy`, plus points around the equator, the prime meridian, the antimeridian and the poles), when `Geohash.encode(…, 6)` and `encodeGeohash(…, 6)` run, then both return the expected cell, and the point lies inside `bounds(cell)`.
2. Given any fart id and valid precise point, when the fuzzer runs, then:
   - `coarseLocationKey` = geohash-6 of the precise point;
   - the public point lies strictly inside that cell, with at least a 10% margin from each edge;
   - running it again with the same id gives the same result;
   - a different id gives a different public point (checked over many ids);
   - the public point never equals the precise point.
3. Given the checked-in vectors file, when the Kotlin host test and the TS unit test run, then both reproduce every vector's cell exactly and its public lat/lng within 1e-9.
4. Given an invalid input (lat outside ±90, lng outside ±180, NaN, a blank fart id), both implementations throw instead of returning a point.
5. Given `npm run seed:farts -- --project fart-map-1a558` or no `--project`, the script exits non-zero without writing. Given a valid target, the docs it builds (unit-tested without Firebase) have exactly the rules' create field set, `visibility_mode` PUBLIC, fuzzed public fields that match `projectPublicLocation`, and a `private/location` doc with the precise point.
6. Given the emulator, a seeded fart doc is listed by the map's PUBLIC query shape for a signed-in user, and its `private/location` can't be read by another user.
7. `scripts/verify.sh --full` is green, and CI (Android, iOS, backend, secret scan) is green.

## Decisions
- **How the epic is split** (`--cross-epics`; recorded here per autopilot §0.4). EPIC-01-03 "Map and markers on both platforms: filters, fuzzed projection, marker parity" (MAP-01/02/03):
  - **-01** (this story): the fuzzed projection in Kotlin + TS, plus the dev fart seed. It comes first because the map needs test data and the seed needs the fuzzer.
  - **-02**: the map host platform capability: Google Maps Compose on Android, MapKit (`MKMapView` through `UIKitView`) on iOS, behind one shared contract (`TechStack.md` §Maps). It renders a list of shared marker models, reports taps and camera/viewport changes, and replaces the Map tab placeholder with a fixed default camera.
  - **-03**: map data and filters: `observeMapFarts(viewport, filter)` with geohash range queries plus the needed composite indexes, the Mine / Followers / Everyone filter (Followers is a humorous empty state, ADR-0020) persisted in `map_filter_last_selected`, MapViewModel loading/empty/success/error/offline states, and the `map_viewed` / `marker_opened` events. The marker detail sheet stays in EPIC-01-05.
  - **-04**: device location: a `LocationProvider` contract (Play Services Location / Core Location), a foreground permission asked on the first "center on me" tap, centering on the user, and a denied state.
- **Map launch vs. permission timing: not decided here.** `Growth.md` §2 says "ask at first map use, never at launch", and `Scope.md` says the map is centered on the user's location. This shapes the launch experience and the permission posture, so it goes to STATE "Pending owner decisions" with a recommended default: the map opens at a default camera without asking, and the first "center on me" tap asks. This story doesn't depend on it. -04 does, and the -02 default camera might; they escalate if it's still open.
- **Jitter algorithm** (ADR-0019 §3 says only "deterministic jitter derived from the fart id"): FNV-1a 32-bit over the UTF-8 bytes of `"<fartId>:lat"` and `"<fartId>:lng"`, each turned into `u ∈ [0, 1)` by dividing by 2³². The public point is `center + (u − 0.5) × 0.8 × cellSize` on each axis, so it stays inside the middle 80% of the cell. FNV-1a is a few lines in both languages with exact integer arithmetic, and the double operations are written in the same order, so Kotlin/JVM, Kotlin/Native and V8 give the same result. Not a secret: the cell is public anyway, and the jitter only stops markers from stacking on the cell center.
- **"Never equals the true position."** If the jittered point equals the precise point (both axes within 1e-9°), the offset is mirrored around the center. If the offset is also zero on both axes (u = 0.5 exactly, so the precise point is the center), a fixed offset of +0.25 × cell size is used on both axes instead. Practically never needed, but it makes the ADR's guarantee hold by construction.
- **The seed bypasses the 18+ PUBLIC rule on purpose.** The Admin SDK skips rules, and `seed_author_dev` has no account doc, so these docs could not be created through rules (ADR-0023 amendment). This is deliberate, dev-only and Admin-SDK-only. The seed is not evidence for the client create path. The emulator test separately proves that a seed doc's shape passes `allow create` for a real 18+ author.
- **`intensity_value` in the seed** cycles non-integer values (0.15 … 0.95), so Node never stores an integer where `DataContracts.md` §3.2 says Float.
- **Invalid input.** `require` (Kotlin) or `throw` (TS). A device fix or a stored doc outside the valid range is a programming error, not a user-facing state. Callers in -04 and EPIC-01-04 hand in platform-validated coordinates.
- **Where the Kotlin code lives.** `core/domain/location`: pure domain logic used by the create flow (EPIC-01-04) and the map's range cover (-03). It isn't a feature, so features don't import each other.
- **Seed content.** Fixed ids and a fixed fake author uid, so re-running replaces rather than piles up. `timestamp_epoch_ms` is spread over the last 7 days so relative times look real. No `users/{seed_author_dev}` profile is written; author display is EPIC-01-05's concern, and the seed can add one then. Dev-only test data, so it isn't the "fake-feeling activity" `map.md` MAP-04 warns about. The allowlist keeps it out of prod.
- **Seed default center.** Istanbul (`41.0082, 28.9784`), the same area the backend test helpers use, spread over about 5 km, changeable with `--center`.

## Plan
**Algorithm (both languages, same operation order):**
- Geohash encode: standard interleaved bisection, even bits = longitude, base32 `0123456789bcdefghjkmnpqrstuvwxyz`. A point exactly on a split goes to the upper half (`>= mid`), as in the reference implementation.
- `bounds(cell)`: replays the bisection to give `latMin, latMax, lngMin, lngMax`. Every step halves a power-of-two-friendly range, so it's exact in IEEE doubles.
- `fnv1a32(s)`: offset 2166136261, prime 16777619, over UTF-8 bytes. Kotlin uses `UInt` arithmetic; TS uses `Math.imul(h ^ b, 16777619) >>> 0`.
- `u = hash / 4294967296.0`; `offsetLat = (uLat - 0.5) * 0.8 * (latMax - latMin)`, `publicLat = (latMin + latMax) / 2 + offsetLat`, the same for lng. If `|publicLat - lat| < 1e-9 && |publicLng - lng| < 1e-9`: when both offsets are 0, use `center + 0.25 * size` on both axes; otherwise use `center - offset` on both axes.
- `GeoBounds.contains(lat, lng)` includes the edges (the precise point may sit on a cell edge, for example `90, 180`). The public point is checked separately against the strict 10% margin.
- Validation: finite numbers, `-90..90`, `-180..180`, non-blank fart id; otherwise throw.

**backend/functions**
- `src/lib/location.ts`: `GEOHASH_PRECISION = 6`, `encodeGeohash`, `geohashBounds` (throws on a char outside the alphabet or an empty cell), `fnv1a32`, `projectPublicLocation(fartId, lat, lng): { public_lat, public_lng, coarse_location_key }`.
- `test/location.test.ts` (unit, vitest):
  - the reference points (acceptance 1). These expectations are independent of our code:
    - `57.64911, 10.40744 → u4pruy` (Wikipedia "Geohash" example);
    - the rest are derived by hand from the bisection definition: `90, 180 → zzzzzz` (every bit 1), `-90, -180 → 000000` (every bit 0), `0, 0 → s00000` (bits `11000…`), `0, -180 → 800000` (bits `01000…`);
    - plus inside-bounds checks;
  - properties over 2,000 generated (id, point) pairs: key = encode, strictly inside with a 10% margin, deterministic, never equal to the precise point;
  - distinct public points for 1,000 ids at one precise point;
  - the mirror branch: feed the projected point back as the precise point → result differs and stays inside;
  - invalid inputs throw;
  - every vector in the fixture matches (cell exact, lat/lng within 1e-9).
- `test/fixtures/location-fuzz-vectors.json`: `{ "vectors": [ { "fart_id", "lat", "lng", "coarse_location_key", "public_lat", "public_lng" }, … ] }`, about 20 entries covering ordinary cities, the edges above, non-ASCII ids (`"ğ💨"`, to pin UTF-8 hashing) and long ids. Generated once with a throwaway node one-liner from the built module and checked in. Its consistency with the implementation is what the TS test asserts, and the Kotlin test checks the same file.
- `src/admin/fartSeed.ts` (pure, unit-testable):
  - `fartSeedDocs({ count, center, nowMs, avatars, sounds }, serverTs)` returns `Record<path, data>` for `farts/seed_fart_NNN` and `farts/seed_fart_NNN/private/location`.
  - Positions come from a deterministic spiral around the center within about 5 km. There is no randomness, so re-runs write the same docs.
  - Public fields come from `projectPublicLocation`; `visibility_mode: "PUBLIC"`; counters 0, `reaction_breakdown {}`, `is_hidden`/`is_removed` false; `flavor_level` 1..5 and `intensity_value` cycled; every third fart gets a `sound_id`, no `description_text`; `timestamp_epoch_ms` spread over 7 days before `nowMs`; `created_at`/`updated_at` = `serverTs`.
  - Validates `count` (1..200) and center ranges.
- `src/admin/seedFarts.ts`: the CLI (`--project`, `--center lat,lng`, `--count`). It reuses `assertSeedTarget` and starter avatars/sounds from `loadStarterCatalog()`, then makes one batched `set` (≤400 writes; count ≤200 × 2 docs). It logs only `{ project, farts }`, never coordinates.
- `assertSeedTarget(project, script = "seed:catalog")`: the error messages name the calling script (a backward-compatible extra parameter).
- `package.json`: `"seed:farts": "npm run build && node lib/admin/seedFarts.js"`.
- `test/fartSeed.test.ts` (unit):
  - the field set equals the rules' create list (required + `sound_id` optional), and no `description_text`;
  - public fields match `projectPublicLocation` of the private point;
  - ids are stable;
  - count bounds;
  - seed target refusals (`fart-map-1a558`, missing).
- `test/emulator/fartSeed.rules.test.ts`: seed `fartSeedDocs` with rules disabled (catalog seeded as well), then:
  - **the shape passes the real create rule:** one seed doc, with `author_user_id` and `fart_id` swapped to a test uid and a fresh id, `created_at`/`updated_at` as server timestamps, and the user's `users/{uid}/private/account` seeded with `AGE_18_PLUS`, is **created** by that 18+ user through rules; the same doc plus an extra field is **denied**. So the hand-copied field list in the unit test can't drift silently;
  - a signed-in user lists `farts` with `where visibility_mode == PUBLIC, is_hidden == false, is_removed == false` and gets them all;
  - another user can't `get` `farts/seed_fart_001/private/location`;
  - signed-out can't list.

**shared** (`commonMain/.../core/domain/location`)
- `Geohash.kt`: `object Geohash { const val PUBLIC_PRECISION = 6; fun encode(lat, lng, precision): String; fun bounds(cell): GeoBounds }` and `data class GeoBounds(latMin, latMax, lngMin, lngMax)`, with `contains(lat, lng)` and center helpers.
- `LocationFuzzer.kt`: `object LocationFuzzer { fun project(fartId, lat, lng): PublicLocation }` and `data class PublicLocation(publicLat, publicLng, coarseLocationKey)`; internal `fnv1a32(String): UInt`.
- Both are `object`s with pure functions, so there's no interface and no Koin binding (there's a single implementation and nothing to fake).
- `commonTest/.../core/domain/location/GeohashTest.kt` and `LocationFuzzerTest.kt`: the same reference points, properties (seeded `Random`), the mirror branch and the invalid inputs as in TS. These run on the JVM host and on the iOS simulator in CI (`:shared:iosSimulatorArm64Test`, which runs `commonTest`). So CI proves, under Kotlin/Native, the reference cells, the properties and the three hard-coded vectors below. The file-based parity test is JVM-only.
- `androidHostTest/.../core/domain/location/LocationFuzzVectorsParityTest.kt`: walks up from `user.dir` to `backend/functions/test/fixtures/location-fuzz-vectors.json` (as in `StarterCatalogParityTest`) and asserts every vector, with the cell exact and lat/lng within 1e-9.
- Native parity: Kotlin/Native doubles are IEEE like the JVM's. To cover the iOS sim without file IO, three vectors are also hard-coded in `LocationFuzzerTest` (commonTest).
