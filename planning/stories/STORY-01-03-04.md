# STORY-01-03-04: Device location and "center on me"

Status: Done   Epic: EPIC-01-03   Features: MAP-01, PRIV-02, PRIV-03 (baseline: permissions)   ADRs: ADR-0019, ADR-0023, ADR-0008, ADR-0004

## Goal
The user can center the map on where they are. Foreground location only, asked the first time they tap "center on me" (owner, issue #25, option C), with friendly denied / blocked / location-off states that keep the map fully usable. Once permission is granted, later app starts open the map on the user's last known location without asking again.

## Scope
- **In:**
  - **`LocationProvider` contract, `core/platform/LocationProvider.kt`:** `permission()` (status, no prompt), `requestPermission()` (prompts when the OS still allows it), `currentLocation(): LocationLookup`, `lastKnownLocation(): DeviceLocation?`, `openAppSettings()`. Its types live in `core/domain/location/DeviceLocation.kt`: `LocationPermission` = GRANTED / NOT_DETERMINED / DENIED / BLOCKED, `DeviceLocation(lat, lng)`, `LocationLookup` = `Found(DeviceLocation)` / `ServicesOff` / `NotAllowed` / `Unavailable`.
  - **Android, `shared/src/androidMain`:** `AndroidLocationProvider` on Play Services Location (`FusedLocationProviderClient.getCurrentLocation` with balanced power accuracy, `lastLocation`), the permission asked through the resumed `ComponentActivity`'s `ActivityResultRegistry` (**coarse only**), `LocationManagerCompat.isLocationEnabled` for location-off, app details settings intent. Manifest: `ACCESS_COARSE_LOCATION` only, no fine and no background permission.
  - **iOS, `shared/src/iosMain`:** `CoreLocationProvider` in Kotlin over `platform.CoreLocation` (`requestWhenInUseAuthorization`, `requestLocation` at hundred-metre accuracy, `location` for the last known fix), `UIApplicationOpenSettingsURLString` for settings. `Info.plist`: `NSLocationWhenInUseUsageDescription` explaining the map.
  - **Map host:** `MapHost.Content` takes a `cameraMoves: Flow<MapCamera>`; each emission animates the camera there (applied after the map has loaded / laid out). Both hosts and `StaticMapHost`.
  - **`MapViewModel`:** `LocateMe` action → permission check/request → current location → `MapEvent.MoveCamera` at street zoom; `isLocating` while it runs; a `LocationNotice` (DENIED / BLOCKED / SERVICES_OFF / UNAVAILABLE) for the failure cases, `DismissLocationNotice`, `OpenLocationSettings`. At start, when permission is already GRANTED, one move to the last known location (no prompt).
  - **`MapScreen`:** a "center on me" button (bottom end, 48 dp+, content description, progress while locating) and the notice card (with "Open settings" for BLOCKED).
  - **Analytics:** `location_permission_result` with `result` (`granted` / `denied` / `blocked`) after each permission request; no coordinates. Observability §11 row.
  - **Docs:** an editorial note on Scope.md MAP-01 and the Growth.md §2 row pointing to the owner decision; `MapScreen.md` lists the locate button and the location notices; STATE; ROADMAP; the EPIC-01-03 manual test plan (last story of the epic).
- **Out:**
  - Background location (never in Phase 1).
  - Using the device location to log a fart, and the precise-location write (EPIC-01-04).
  - Showing the user's own position dot (the blue dot) on the map: not specified; centering is enough for MAP-01. Others never see it in any case.
  - Opening the system location-services page (iOS can only open the app's settings; parity keeps both to a message).

## Acceptance
1. **No prompt at launch.** Given a user who never granted location, when the app opens, then the map shows the default camera (or the last camera of this session) and no permission prompt appears (VM test: no `requestPermission` call without `LocateMe`; device: test plan).
2. **First tap asks.** Given permission NOT_DETERMINED (or DENIED on Android, where the OS may ask again), when the user taps "center on me", then the OS prompt appears once; on GRANTED the map animates to the current location at street zoom (VM test: `MoveCamera` with the found point; device: test plan).
3. **Granted later starts.** Given permission already GRANTED at start and a known location (the cached fix, or a quick one-shot fix within a few seconds), the map moves there once without a prompt; with no location the default camera stays; if the user moved the camera before the location arrived, the start move is skipped (VM tests). Tapping "center on me" while GRANTED moves without a prompt.
4. **Denied / blocked / off.** A denial shows the DENIED notice (tap again to retry); a blocked permission (Android "don't ask again", iOS denied/restricted) shows the BLOCKED notice with "Open settings", which calls `openAppSettings()`; location services off shows SERVICES_OFF; no fix (timeout/failure) shows UNAVAILABLE. A request that ends undecided (NOT_DETERMINED: the Android Activity was recreated under the prompt) shows nothing and tracks nothing. In every case the map, filters and markers keep working and nothing crashes. The notice is dismissible and the next tap replaces it (VM tests per case; device: test plan).
5. **One at a time.** A tap while a lookup is running does nothing; `isLocating` is true during the lookup and false after every outcome (VM test).
6. **Privacy.** Only the coarse foreground permission is declared and asked on Android (no `ACCESS_FINE_LOCATION`, no `ACCESS_BACKGROUND_LOCATION`); iOS has only the when-in-use string and asks for hundred-metre accuracy. The device location never reaches logs or analytics: `location_permission_result` carries only `result` (AnalyticsEventTest asserts the params), provider logs carry categories only (code-review checklist). The location becomes the camera only; it isn't stored in State, preferences or Firestore.
7. **Analytics.** `location_permission_result` fires once per permission request with `granted` / `denied` / `blocked`; never when permission was already GRANTED, already BLOCKED (iOS status, or a BLOCKED result earlier in this session on Android: the VM remembers it and skips the request), or when the request ended undecided (VM tests).
8. **Camera moves on both hosts.** A `MoveCamera` animates the Android (Google Maps) and iOS (MapKit) camera; a move that arrives before the map has a size is applied when it does; the resulting camera is reported through `onCameraIdle`, so it survives a tab switch (device: test plan; compile: both hosts).
9. **Parity:** Android and iOS implement the full contract in this PR.
10. `scripts/verify.sh --full` is green; CI (Android, iOS link + xcodebuild, backend, secret scan) is green.

## Decisions
- **Permission timing (owner, 2026-11-26, issue #25: option C).** The first ask happens on the first "center on me" tap, never at launch. Once permission is granted, later app starts open on the last known location without asking again. Scope.md MAP-01 ("centered on user location") and Growth.md §2 get an editorial note pointing to this.
- **Coarse only on Android (plan review).** Centering the map needs no more than approximate location, so the app declares and asks for `ACCESS_COARSE_LOCATION` only. Asking for precise location now, for a later story's sake, would settle a privacy question early. EPIC-01-04 (logging, the owner-only precise point) decides whether it adds fine location, with its own in-context ask. iOS has no app-level "coarse only" switch except `NSLocationDefaultAccuracyReduced`, which is app-wide and would pre-decide EPIC-01-04, so iOS asks for when-in-use with `kCLLocationAccuracyHundredMeters` and the user keeps the system's Precise toggle. Source: tie-break "safer for privacy" (WorkingAgreement §6), `ContentSafety.md` (location is the highest-risk surface), PRIV-02.
- **Start move: cached fix first, a short one-shot fix second (plan review).** The start move uses the cached fix; when there is none (a fresh iOS manager often has none), a one-shot fix with a 5 s limit. If the user moved the camera (a camera different from the first one the map reported) before it arrives, the move is skipped, so it never fights a pan. No location → the default camera stays. Source: Acceptance 3 on both platforms; Growth.md favors an instant map.
- **Camera moves are a one-time effect.** `MapEvent.MoveCamera` (ADR-0004: effects are Events), passed to the host as a `Flow<MapCamera>`; the host applies each move once and reports the new camera through `onCameraIdle`, so State stays the single source of the camera after the move. A move sent before the map is composed waits in the event buffer. A move the host has received but not finished animating when the user switches tabs is lost (the camera stays where the animation stopped); accepted. A move buffered while the Map tab is off-screen (the start move, if the user switched tabs before it arrived) is applied when they come back; accepted, it's their own location.
- **Street zoom 15** for "center on me" (neighborhood scale, same as Google Maps' "my location" feel). Implementation detail.
- **No blue dot.** Not in any spec; adding the SDK's my-location layer needs its own permission plumbing in both hosts. Centering is what MAP-01 asks for.
- **Android "blocked" detection.** Android doesn't report "don't ask again"; after a denied request, `shouldShowRequestPermissionRationale` false means blocked (the standard heuristic), in a pure `androidPermissionResult(granted, showRationale)` function with a host test. Before any request, Android status is GRANTED or NOT_DETERMINED (it can't tell never-asked from denied), so the VM requests when not granted and lets the OS decide.
- **Analytics per real request (plan review).** `location_permission_result` fires after each `requestPermission()` that returns a decision. The VM remembers a BLOCKED result for the session and shows the BLOCKED notice on later taps without requesting again, so an Android user who chose "don't ask again" doesn't inflate the event. Observability §11 gets the row (the table is the event contract).
- **Notices, not errors.** Denied / blocked / off are user choices or device states, shown as a dismissible card in the product voice, not as the data error card. UNAVAILABLE (no fix) is logged as a warning with the reason category.
- **Activity recreated during the Android prompt (plan review).** The registry callback is tied to the Activity that launched the prompt. If that Activity is destroyed first, the request completes with GRANTED if the permission is held by then, else NOT_DETERMINED; the VM shows nothing and tracks nothing for NOT_DETERMINED, so the button never stays stuck and no false notice or event appears. The user taps again. The launcher uses the registry's lifecycle-less `register(key, contract, callback)` with a unique key, unregistered on every exit; a lifecycle observer on the same Activity only watches for `ON_DESTROY`. A resumed Activity that isn't a `ComponentActivity` (none in this app) or no resumed Activity → a warn log and the current status.
