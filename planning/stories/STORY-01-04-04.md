# STORY-01-04-04: Log Fart drafts (autosave, restore, keep-or-discard on back)

Status: Done   Epic: EPIC-01-04   Features: CREATE-03 (`DRAFT` state, step 10 failure), CREATE-03.3   ADRs: ADR-0004, ADR-0019, ADR-0022, ADR-0023

## Goal
Nothing a user types into Log Fart is lost. The form saves itself as they go. If the app is killed, or a submit fails, the next open picks up where they left off. Leaving a half-filled form asks whether to keep the draft or throw it away.

## Scope
- **In:**
  - **`log_draft`** (LocalData.md §5) in the existing DataStore file: a `LogDraftRepository` (`feature/logfart/domain`) with a DataStore implementation (`feature/logfart/data`). The key is user-scoped, so sign-out wipes it.
  - **Autosave:** once the user has changed something (a "dirty" form), the form is saved shortly after each change while editing (`DRAFT`) or after a failure (`FAILED`).
  - **Restore on open:** a saved draft for the same account fills the form back in: a picked time, avatar, sound, flavor, intensity, caption and visibility, each one checked again. A short "Picked up where you left off" note shows.
  - **Location is never stored in the draft**, neither a device fix nor a placed pin. The location step runs again at open (Decisions).
  - **Cleared on hand-off** (SUCCESS and OFFLINE) before the screen closes. **Kept on failure:** saved right away, and every field stays.
  - **Keep-or-discard on back** (close button, system back, iOS swipe) for a dirty form. A clean form closes straight away.
  - **`log_abandoned`** with `step_reached` (Observability.md §11; moved here from STORY-01-04-02).
- **Out:**
  - Several drafts, a drafts list, or draft expiry (none is specified).
  - "Clear draft cache" in Settings (EPIC-01-07).
  - The account-link nudge (-06). Delete (-05).

## Acceptance
1. **Clean form saves nothing.** Given a fresh screen where the user changed nothing (a device fix found by itself doesn't count), no draft is written, and Close emits `Closed` at once with no dialog.
2. **Autosave.**
   - Given the user changes a field (time, avatar, sound, flavor, intensity, caption, visibility) or confirms a pin, the draft is saved `DRAFT_SAVE_DELAY` (500 ms) after the last change, carrying exactly the current values.
   - Nothing is saved while `UPLOADING`, including a change made just before submit (the pending save is dropped).
   - A failed save is logged by the repository and the form keeps working.
3. **What's in a draft.**
   - Stored: the owner uid, avatar, sound, flavor, intensity, raw caption and visibility.
   - The time is stored only when the user picked it, else null.
   - No coordinates, ever.
4. **Restore.** Given a stored draft with the same uid, opening Log Fart restores the stored fields, sets `restoredDraft = true` and marks the form dirty. Each value is checked again:
   - an invalid flavor, intensity or caption length is ignored or limited, using the same reducers as user input;
   - a visibility that isn't allowed for the age band falls back to the ADR-0023 default;
   - a null time keeps this open's time; a stored time is used and counts as picked;
   - the location step runs as for a fresh open;
   - an avatar or sound that isn't usable yet stays pending until it becomes usable (an owned item arriving later). It is dropped when the user picks in that row, or once both the catalog and the owned set have loaded without making it usable.
5. **Live input wins.** If the user has already changed something before the draft finishes loading, the stored draft is not restored, and the next autosave replaces it.
6. **Other account.** A stored draft whose uid isn't the active one is not restored, and it is cleared.
7. **Hand-off clears.** On SUCCESS or OFFLINE, the autosave and any save in flight are cancelled, then the stored draft is cleared, then `Finished` is sent. Draft writes are serialized, so nothing writes the draft back.
8. **Failure keeps.** On a failed `createFart` with a dirty form, the draft is saved at once with every field, and the state still holds them. A new ViewModel on the same store (process death) restores them.
9. **Keep or discard.**
   - Close on a dirty form in `DRAFT` or `FAILED` (picker closed) emits `ConfirmLeave` and doesn't close.
   - `KeepDraftAndLeave` saves the draft at once (no delay), then emits `Closed`, even if the save failed (it is logged).
   - `DiscardDraftAndLeave` clears it, then emits `Closed`.
   - Both are ignored unless the status is `DRAFT` or `FAILED`.
   - Dismissing the dialog leaves the form as it is.
   - Close while uploading is still ignored, and Close with the picker open still closes only the picker.
10. **`log_abandoned`.** Every exit without a hand-off (a clean Close, Keep, Discard) tracks `log_abandoned` once, with `step_reached`:
    - `location`: no point resolved yet;
    - `details`: a point is resolved;
    - `failed`: the last submit failed.
11. **Storage.**
    - The DataStore draft round-trips every field, including a null time, sound and visibility.
    - A corrupt value is logged without its content, reads as no draft and is removed.
    - A blank owner uid reads as no draft, and an unknown visibility reads as PRIVATE.
    - A read `IOException` is logged and reads as no draft. A write `IOException` is logged and returned as a typed failure.
    - `clearUserScoped()` (sign-out) removes `log_draft`.
12. `scripts/verify.sh --full` is green, and CI (Android, iOS, backend, secret scan) is green.

## Decisions
- **Where the draft lives.** A feature-owned `LogDraftRepository` (domain interface + DataStore implementation in `feature/logfart/data`), on the same DataStore file as the preferences.
  - The key is declared once, in `DataStorePreferencesRepository` (internal), and listed in `USER_SCOPED_KEYS` so sign-out wipes it (LocalData.md §7.4: "draft").
  - This keeps the draft's type out of `core` and keeps one list of user-scoped keys.
  - Source: LocalData.md §5/§7, kotlin-shared rules ("where code goes"), tie-break "simpler".
- **No coordinates in the draft (plan review, blocker).**
  - Android has `allowBackup="true"` with no exclusion rules, and STORY-01-03-04 accepted that only because nothing location-related is stored on the device.
  - Persisting a precise pin would copy owner-only precise coordinates (ADR-0019) into cloud backups. That changes the privacy posture, which only the owner decides.
  - So neither the device fix nor a placed pin is stored. After a restore the location step runs as usual (a fresh fix, or the user re-pins).
  - Storing the pin together with a backup exclusion would be a Proposed-ADR question if it's ever wanted.
  - The caption (possibly for a PRIVATE log, or one later discarded) and the cosmetic picks can reach the user's own device backup. They are the user's own text in the user's own backup, and none of it is location. LocalData §5 says so.
  - Source: ADR-0019, LocalData.md §5, STORY-01-03-04 Decisions, tie-break "safer for privacy".
- **"Dirty" = the user changed something** (an accepted field edit, a visibility pick, a confirmed pin), or the form came from a draft.
  - A device fix found by itself, or opening the screen, isn't user input.
  - So a clean quick log never leaves a draft behind and never asks on back.
  - A confirmed pin dirties the form even though the pin isn't stored, so back asks before throwing that work away.
  - Source: CREATE-03 step 10 ("no user input is lost"), DesignSpecification "Drafts are preserved", tie-break "simpler".
- **Autosave is debounced at 500 ms** while `DRAFT` or `FAILED`.
  - Typing a caption doesn't write DataStore on every key, and at most half a second of input is at risk if the process dies mid-typing.
  - Keep and failure save at once.
  - Source: CREATE-03.3 `DRAFT` ("survives app kill and process death").
- **The time is kept only when the user picked it (plan review).** An untouched time is the screen-open default, so a draft restored days later uses the new open time instead of silently backdating the fart. A time the user chose is restored as chosen. Source: CREATE-03.1 step 2.
- **Restored values go through the same validation as input,** and the visibility through the allow-list. A draft can never carry PUBLIC to a 13–17 user, or a locked item into a fart. Source: ADR-0023 amendment, CREATE-03.2.
- **Pending avatar or sound.**
  - The options first emit the starter set, before the catalog and the owned set arrive, so restoring an owned avatar directly would reset it to the default.
  - The restored id waits in state until it is usable. It is dropped when the user picks in that row, or once both the catalog and the owned set have emitted real values without making it usable (a removed item, a revoked grant).
  - Meanwhile the autosave writes the pending id, so a second process death doesn't lose it.
  - Source: STORY-01-04-03 (options flow), plan review.
- **Live input wins over a late restore (plan review).** The form is editable while the draft loads. If the user already changed something, the old draft isn't applied over their input. Source: CREATE-03 step 10 ("no user input is lost").
- **The draft carries the owner uid,** and one from another uid is cleared instead of restored. Sign-out already wipes the key; the uid check covers a wipe that failed (LocalData §7: "a failed wipe … no automatic retry yet"). Source: LocalData.md §7, tie-break "safer for privacy".
- **Keep with a failed save still leaves (plan review).**
  - The user asked to leave, and a DataStore write fails only on a disk error.
  - Holding them on the form with an error they can't fix is worse, and the repository logs the failure.
  - The same applies to the save after a submit failure: the fields stay on screen anyway.
  - Source: tie-break "simpler", kotlin-shared rules (errors logged, never swallowed).
- **Draft writes are serialized** through one `Mutex`, and the hand-off cancels the autosave and failure-save jobs before it clears. A late save can't resurrect a posted draft (plan review).
- **Corrupt draft logging** carries only the event `log_draft_corrupt` and the exception class name, never the message, because a serialization message can quote the JSON and with it the caption (plan review). Source: Observability.md (no free text), Security.md.
- **Leave dialog.**
  - A Material 3 `AlertDialog` on both platforms: "Keep draft" (confirm) and "Discard" (dismiss button). It opens through a `ConfirmLeave` event and is held in `rememberSaveable` UI state, so it survives rotation, like the voice sheet.
  - Tapping outside or back dismisses it and stays on the form. Discard is the destructive choice, so it is an explicit button.
  - Source: LogFartScreen.md ("back from draft prompts safe discard or preserves draft"), DesignSpecification ("destructive actions require confirmation"), compose-ui rules.
- **Restored note.**
  - An inline note at the top of the form ("Picked up where you left off."), shown while the screen is open.
  - It's state, not a snackbar, because the screen has no snackbar host.
  - It has no dismiss and no "start over" button: back → Discard does that. It is added to LogFartScreen.md.
  - Source: tie-break "simpler".
- **`log_abandoned.step_reached` values** are `location` / `details` / `failed`, added to Observability.md §11 (the contract named the parameter but no values). The values are categories only, with no field contents. Source: Observability.md §6/§11.
- **A failed clear after a hand-off** is logged by the repository. The next open would then restore the already-posted fart's fields, and the user can discard them. It's rare (a disk error) and the loss is small.
- **Privacy and monetization implications.**
  - The draft stays on the device (the DataStore file) and is user-scoped, so sign-out wipes it.
  - It holds no coordinates. The caption is never logged (`LogDraft.toString` omits it), and analytics carry `step_reached` only.
  - Nothing new is sent to the server.
  - No monetization surface changes, and a restored locked item stays locked.

## Plan
**shared `feature/logfart/domain/LogDraft.kt`**
- `data class LogDraft(ownerUid, timestampEpochMs: Long?, avatarId: String, soundId: String?, flavor: Int, intensity: Double, description: String, visibility: VisibilityMode?)`, with a `toString` that omits the description.
- `interface LogDraftRepository { suspend fun load(): LogDraft?; suspend fun save(draft: LogDraft): AppResult<Unit>; suspend fun clear(): AppResult<Unit> }`. KDoc: never throws; a read error or a corrupt value is logged and reads as null.

**shared `feature/logfart/data/DataStoreLogDraftRepository.kt`**
- `@Serializable internal data class LogDraftDto` with defaults on every field: `owner_uid`, `timestamp_epoch_ms` (nullable), `avatar_id`, `sound_id`, `flavor`, `intensity`, `description`, `visibility` (wire name, nullable).
- Mapping: `toDomain(): LogDraft?` and `LogDraft.toDto()`. A blank `owner_uid` → null, and an unknown visibility → PRIVATE via `VisibilityMode.fromWire`.
- `Json { ignoreUnknownKeys = true }`.
- `load()`:
  - read `store.data.first()[LOG_DRAFT]`;
  - on `SerializationException` / `IllegalArgumentException`: warn `log_draft_corrupt` with `attributes = mapOf("exception" to class simpleName)`, no message, then remove the key;
  - on `IOException`: error log and null.
- `save` / `clear`: `store.edit`; an `IOException` → typed failure + structured log (the same shape as `DataStorePreferencesRepository.write`).
- `DataStorePreferencesRepository.companion`: `internal val LOG_DRAFT = stringPreferencesKey("log_draft")`, added to `USER_SCOPED_KEYS`.
- Koin `dataModule`: `single<LogDraftRepository> { DataStoreLogDraftRepository(store = get(), logger = get()) }`.

**shared `core/observability/Analytics.kt`**
- `LogAbandoned(step: LogStep)` → `log_abandoned`, `step_reached` = `location` / `details` / `failed`; `enum class LogStep`. `AnalyticsEventTest` +1.

**shared `feature/logfart/presentation`**
- `LogFartState` gains:
  - `isDirty: Boolean = false`, `timePicked: Boolean = false`, `restoredDraft: Boolean = false`;
  - `pendingAvatarId: String? = null`, `pendingSoundId: String? = null`.
- `reduce` (`LogFartDetails.kt`): every accepted edit sets `isDirty = true`.
  - `DateTimePicked` also sets `timePicked = true`.
  - An accepted `AvatarSelected` clears `pendingAvatarId`, and an accepted `SoundSelected` clears `pendingSoundId`.
  - A rejected tap on a locked item changes nothing.
- `LogFartDraft.kt` (pure, unit-tested):
  - `LogFartState.toDraftOrNull(uid): LogDraft?`: non-null only when `isDirty` and the status is DRAFT or FAILED. The time is set only if `timePicked`, the avatar is `pendingAvatarId ?: avatarId`, and the sound is `pendingSoundId ?: soundId`;
  - `LogFartState.restore(draft, defaultVisibility): LogFartState`:
    - the time, if non-null, with `timePicked = true`;
    - flavor, intensity and caption through `withFlavor` / `withIntensity` / `withDescription`;
    - visibility kept if in `allowedVisibilities`, else the given default;
    - avatar and sound applied if usable, else pending;
    - `isDirty = true`, `restoredDraft = true`;
  - `LogFartState.applyPending(optionsLoaded: Boolean)`: a pending id that is now usable becomes the selection and the pending clears. If `optionsLoaded` and it is still unusable, the pending is dropped;
  - `LogFartState.abandonStep()`: FAILED → `failed`; a resolved point → `details`; otherwise `location`.
- New actions: `KeepDraftAndLeave`, `DiscardDraftAndLeave`. New event: `ConfirmLeave`.
- `DraftAutosave` (presentation helper class, so the ViewModel stays under detekt limits; created by the VM with its scope):
  - holds the `LogDraftRepository`, a `Mutex`, the autosave `Job` and the failure-save `Job`;
  - `start(states: Flow<LogDraft?>)`: `distinctUntilChanged().debounce(DRAFT_SAVE_DELAY).filterNotNull().collect { write { save(it) } }`. A null (UPLOADING, clean) supersedes a pending value inside the debounce window, so it is dropped;
  - `saveNow(draft)` (suspend) and `saveSoon(draft)` (the failure-save job);
  - `stop()`: cancels both jobs;
  - `clear()`: `stop()`, then `write { clear() }`.
- `LogFartViewModel(..., drafts: LogDraftRepository, ...)`:
  - `loadSessionData`, after the visibility default:
    - `drafts.load()`. If the uid is the same and the state is not dirty → `setState { restore(draft, default) }`. If the uid is the same but the state is already dirty, don't restore. If the uid is another one → `drafts.clear()`;
    - then `autosave.start(state.map { it.toDraftOrNull(uid) })`;
    - the cosmetics `combine` tracks whether each source has emitted a real value (`catalogLoaded && ownedLoaded`) and applies `withOptions(...).applyPending(loaded)`.
  - `VisibilitySelected` (accepted) and `ConfirmPin` set `isDirty = true`.
  - `onClose`:
    - while uploading → ignore;
    - picker open → close the picker;
    - dirty and status DRAFT/FAILED → `ConfirmLeave`;
    - otherwise → `leave()`: track `LogAbandoned` unless the status is SUCCESS/OFFLINE, then emit `Closed`.
  - `KeepDraftAndLeave` (only in DRAFT/FAILED): `autosave.stop()`, then `saveNow(snapshot)` if non-null, then `leave()`.
  - `DiscardDraftAndLeave` (only in DRAFT/FAILED): `autosave.clear()`, then `leave()`.
  - Both run in `viewModelScope` and await the store before `Closed`, for the same reason as the visibility save: `Closed` pops the screen and cancels the scope.
  - `onHandedOff`: `autosave.clear()` before `setLastVisibilityMode` and `Finished`.
  - `onFailed`: `toDraftOrNull` non-null → `autosave.saveSoon(it)`.
- `SharedModules`: `drafts = get()`.
- `LogFartScreen.kt`:
  - `LogFartEntry` collects `ConfirmLeave` → `showLeaveDialog = true` (`rememberSaveable`) → `LeaveDraftDialog(onKeep, onDiscard, onDismiss)` in `LogFartDraftUi.kt`;
  - `RestoredNote` card at the top of the form when `state.restoredDraft`;
  - strings `log_draft_restored`, `log_leave_title`, `log_leave_body`, `log_leave_keep`, `log_leave_discard` in the product voice;
  - previews: the restored note, the leave dialog content.
