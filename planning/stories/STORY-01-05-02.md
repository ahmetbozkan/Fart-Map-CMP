# STORY-01-05-02: Reactions: five types, one per user, toggle and replace

Status: Done   Epic: EPIC-01-05   Features: SOCIAL-01 (reactions), MAP-02 (counts on the marker detail)   ADRs: ADR-0015, ADR-0020, ADR-0023

## Goal
A user reacts to a fart from its detail sheet with one of the five free reactions (SOCIAL-01). Tapping the active reaction again removes it; tapping another replaces it. The reaction shows at once (optimistic); the counts come from the fart's parent document, maintained by a Cloud Function (ADR-0015), so they are never computed on the client.

## Scope
- **In:**
  - **Domain (`feature/map/domain`):** `ReactionType` (DEAD / TOXIC / RIP / SMELLED / LEGEND, the wire names of DataContracts §3.3), `ReactionRepository` (`observeOwnReaction(fartId, uid)`, `setReaction(uid, fartId, type?)`). `MapFart` += `reactionCount: Int = 0`, `reactionBreakdown: Map<ReactionType, Int> = emptyMap()`.
  - **firebaseData:** `FirestoreReactionRepository` (`farts/{id}/reactions/{uid}`, one batch launched in `AppWriteScope`, never awaited). `MapFartDto` reads `reaction_count` and `reaction_breakdown` (unknown keys dropped).
  - **Presentation:** `ReactionsViewModel` (`StateViewModel`, keyed by fart id): State = own reaction + the five labels; Actions = `Toggle(type)`; no Event. The detail sheet hosts a `ReactionBar` (five toggles with their label and count, selected state as text as well as shape).
  - **Backend:** `triggers/reactionWritten.ts` (`onReactionWritten`, `farts/{fartId}/reactions/{userId}`): applies the count delta (create +1, delete −1, type change moves one unit between breakdown keys) inside `runOnce`, in a transaction on the parent. Exported in `index.ts`, added to `PROD_FUNCTIONS`.
  - **Strings:** `composeResources/values/strings.xml`: five reaction labels (SOCIAL-01 wording), the count and selected descriptions.
  - **Analytics:** none in this story (no event in the contract yet; see Decisions).
- **Out:**
  - Report and Block (-03), the marker sound (-04).
  - Reaction push (ADR-0020 NOTIF-01 minimal): a separate fan-out, not in the -02 roadmap line.
  - Comments (SOCIAL-02, Phase 2).
  - A numeric per-user reaction rate limit (see Decisions).
  - Changes to the create/update rules (they already enforce shape, type enum, one per user, read eligibility and blocks).
  - **Changed in review:** the read rule is tightened to the reacting user's own doc by `get` (no `list`), so reactor ids are never listable (security review; DataContracts §3.3). Covered by `social.rules.test.ts`.

## Acceptance
1. **One reaction per user per fart.** Writing a reaction creates or replaces `farts/{id}/reactions/{uid}`; the doc id is the uid, so a second reaction never adds a second doc.
2. **Toggle and replace.** Tapping the active reaction removes it (delete); tapping another replaces it (type change). The chip shows the new state at once, before the write completes.
3. **Silent rollback.** When the write is rejected or the cache reverts the doc, the chip returns to the observed reaction without an error dialog. The rejection is logged with a structured event (no content).
4. **Counts come from the parent.** The sheet shows `reaction_count` and each type's `reaction_breakdown` from the loaded fart. The client never writes the parent's counters (rules), and the trigger keeps them equal to the reaction docs.
5. **Trigger correctness.** `onReactionWritten` (emulator test): create → count +1 and breakdown[type] +1; delete → count −1 and breakdown[type] −1; type change → count unchanged, breakdown moves one unit; a redelivered event runs once (`runOnce`); a missing parent is a skip, not a crash; logs carry no coordinates.
6. **Mapper.** `MapFartDto` maps `reaction_count` (absent → 0) and `reaction_breakdown` (absent → empty; unknown type keys dropped; negative values clamped to 0). Covered by `MapFartDtoTest`.
7. **Eligibility.** Reactions use the rules' read eligibility and block check (already in `farts.rules`/`social.rules` tests); the client shows the bar only on farts in State (already readable).
8. **Parity.** Compose and shared code only; both platforms render the same bar. iOS compiles in CI.
9. `scripts/verify.sh --full` green on Windows (iOS and the emulator suites in CI); CI green on the PR.

## Decisions
- **Trigger, not client counters.** Counts are maintained by `onReactionWritten` (ADR-0015, DataContracts §3.3); the client never writes them (rules already deny). Source: DataContracts §3.2 ("maintained by a Cloud Function trigger").
- **Counts lag one round trip.** The bar shows the parent's counts as loaded; the chip (own reaction) is the optimistic part. A client-side count overlay would duplicate the trigger's arithmetic and drift. Source: `SocialSystems.md` §2 ("optimistic update" applies to the reaction state machine; counts "always visible").
- **Own reaction via a listener on `reactions/{uid}`.** The write path reports pending writes through the cache, so a rejected write reverts the chip without extra code. One listener per open sheet, in a `ReactionsViewModel` keyed by fart id, so `MapViewModel` keeps its six dependencies (detekt `LongParameterList`, no suppression). Source: STORY-01-05-01 decision (the sheet itself reads no new fart doc; a reaction read is new and needed).
- **Rollback is silent in the sheet.** The shell's write-rejection monitor is global; a reaction rejection shows the generic snackbar only if `PendingWriteMonitor` reports it. Flagged for review rather than special-cased. Source: `SocialSystems.md` §2 (silent rollback); `LocalData.md` §3.
- **Numeric rate limit deferred.** `Security.md` §3 asks for reaction-flood dampening, but no docs number a limit. The enforced limits are the rules' (one per user per fart, type enum, read eligibility, blocks) plus this story's transaction. A numeric limit needs an owner-set number; recorded for `ContentSafety.md` follow-up, not guessed. Source: `Security.md` §3; `ContentSafety.md` §106.
- **Own farts can be reacted to.** The rules allow it and `SocialSystems.md` §2 rule 4 only restricts by visibility. Shown on all farts in State.
- **No analytics event.** `SocialSystems.md` defines the reaction loop but not a reaction event in `AnalyticsEvent`; adding one is a contract change (analytics-event skill) and not in the -02 line. Deferred to the -03/-04 analytics pass.
- **Labels follow SOCIAL-01.** Dead (laughing), Toxic (fire), RIP (skull), Smelled it (nose), Legend (crown); wire names unchanged. Source: `SocialSystems.md` §2 reaction set.
