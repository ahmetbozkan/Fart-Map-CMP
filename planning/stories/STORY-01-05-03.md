# STORY-01-05-03: Safety: report, block, auto-hide at 3

Status: Done   Epic: EPIC-01-05   Features: MOD-01 (report + block), MOD-02 (baseline: intake, auto-hide at 3), PRIV-01 (block)   ADRs: ADR-0015, ADR-0019, ADR-0023

## Goal
On someone else's fart, the detail sheet offers **Report** (a reason sheet, then a short thank-you) and **Block** (a confirmation). After a block the blocker no longer sees the blocked user's farts on the map, and the server already refuses reactions and FOLLOWERS reads across the block in both directions. A fart reported by 3 distinct users is hidden from the public map by the backend until moderation reviews it (ADR-0015). This is the Phase 1 safety floor (`ContentSafety.md` §4: "no social feature ships without Block + Report").

## Acceptance
1. **Report and Block are offered on others' farts only.** On another user's fart the sheet shows Report and Block; on an own fart it shows Delete and neither safety action.
2. **Report flow.** Tapping Report opens a reason sheet with the seven reasons; Submit is disabled until one is picked. Submit writes `moderation_reports/{uid}_FART_{fartId}` (`target_type FART`, `reason_code`, `status OPEN`), never awaited, works offline, and the sheet shows a thank-you with Done. `report_submitted` (`target_type=fart`, `reason_code`) is tracked.
3. **A repeated report is harmless.** A second report of the same fart by the same user shows the same thank-you; the server refuses it (create-only id, existing rules test) and the rejection is only logged, with the operation name and never the report id or reporter.
4. **Block flow.** Tapping Block opens a confirmation that says unblocking comes later in Settings. Confirm writes `blocks/{uid}_{authorUid}` (never awaited, works offline), and the author's farts leave the blocker's map at once from the local cache, which also closes the open sheet. Cancel changes nothing. `block_applied` (`target_type=user`) is tracked. The blocked user is not told.
5. **Blocker-side hiding.** `ObserveVisibleMapFarts` drops farts by users the caller blocked from every map update; the caller's own farts are never dropped; `Failed` passes through.
6. **Fail-safe reads.** The blocked-uids flow starts with an empty set and, if its listener fails, logs and keeps the last known set, so the map never waits on or is blanked by it.
7. **Auto-hide.** `onReportCreated` (emulator test): a FART report increments `report_count`; the third distinct reporter sets `is_hidden = true`, and the fart leaves the public map query; a redelivered event counts once (`runOnce`); a report by the fart's author, a non-FART target, a malformed report, a missing fart or a removed fart is a logged skip; logs carry the fart id and outcome only (never the reporter).
8. **Parity.** Compose and shared code only; iOS compiles in CI.
9. `scripts/verify.sh --full` green on Windows (iOS and the emulator suites in CI); CI green on the PR.

## Decisions
- **Blocked user's side of hiding escalated, not decided.** Hiding the blocker's PUBLIC farts from the blocked user needs the blocked user's client to know who blocked them (rules can't filter PUBLIC queries, DataContracts §5.2), and `SocialSystems.md` §5 says a block is never surfaced. Plan review flagged widening the `blocks` read as a privacy/security posture change (WorkingAgreement §6). This story ships the blocker side; issue #37 asks the owner (recommended: blocker-side only for Phase 1). Follow-up STORY-01-05-05 waits on it.
- **Reason list (seven codes).** `HARASSMENT` (harassment, threats, hate), `PRIVATE_INFO` (doxxing or someone's location), `MINOR_SAFETY` (puts a minor at risk), `SEXUAL`, `ILLEGAL`, `SPAM`, `OTHER`. Derived from the policy lines in `ContentSafety.md` §6 and the minors escalation in §5; the FartDetailSheet spec lists "report reason list copy" as unresolved. Copy follows the voice but stays plain for safety topics. The codes are listed in DataContracts §3.12. Review order (MINOR_SAFETY first) is in `OwnerTodo.md`.
- **Report target is FART only in this story.** Profiles of other users arrive with EPIC-01-07 (Scope.md lists "farts and profiles"); the USER target is wired in the rules already. Source: ROADMAP EPIC-01-07.
- **No local "already reported" memory.** A repeat report is refused by the create-only id rule and only logged (`write_rejected` with the op name); the user sees the same thank-you. Reports aren't readable by the reporter (DataContracts §5.6), so the client couldn't check anyway.
- **Thank-you inside the sheet, not a snackbar.** `Security.md` §5 asks for "local confirmation"; the map has no snackbar host and the shell surfaces only fart rejections.
- **Auto-hide counts in the trigger.** Distinctness comes from the report id (`{reporter}_{type}_{target}`, create-only); `onReportCreated` increments `report_count` in a transaction under `runOnce` and sets `is_hidden` when the count reaches 3. An author's self-report doesn't count (the UI doesn't offer it; the author can delete instead), and a removed fart isn't counted. No new fields. Source: DataContracts §3.2 (`is_hidden`: "true after 3 distinct reports pending review"), ADR-0015.
- **Known abuse vector, flagged to the owner.** Anonymous accounts are cheap, so three of them could hide a fart. App Check (STORY-01-02-05, deferred, release-blocking) and manual review are the mitigations; a smarter threshold needs an owner decision, listed under STATE "Pending owner decisions".
- **Block hiding is a domain use case.** `ObserveVisibleMapFarts` holds the filter logic (Architecture: use cases only when they hold logic) and replaces `MapFartRepository` in `MapViewModel`, so the ViewModel keeps six dependencies (detekt `LongParameterList`, no suppression).
- **Blocks listener failure shows content rather than blanking the map.** The flow starts empty and a failed listener keeps the last set; failing closed would empty the whole map for one read error. Rules still enforce blocks on reactions and FOLLOWERS reads.
- **Unblock waits for Settings (EPIC-01-07).** PRIV-01 puts the block list in Privacy settings. Until then a block can't be undone from the UI; the confirmation says so plainly.
- **Report review is an owner task.** Reports are readable only through the Admin SDK / console (DataContracts §5.6). `OwnerTodo.md` gets a review item (where, how often, MINOR_SAFETY first, and how to un-hide).
